# 源码统计与 ECS 性能审查

后续进展：[首批优化实现与对照结果](ecs-optimization-first.md)。本文保留优化前的统计和审查快照。

2026-10-25；基于提交 `5e85e31` 的工作区。本轮新增统计脚本与审查基准，ECS 生产实现未改动。以下性能数字是当前实现的基线，不是优化后的提升。

## 代码行数

使用 cloc 1.98，统计跨平台源码，不受当前 Go build tags 限制。`Code` 是去掉空行和纯注释行后的物理源码行数，不是语句数。字符串、嵌入源码和数据表仍属于源码；代码与注释混合的一行按代码行统计。解析口径以 cloc 为准。

| 范围 | 文件数 | 有效代码行 | 空行 | 注释行 | 总行数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全部非测试源码 | 869 | 461,323 | 19,582 | 12,305 | 493,210 |
| 再排除示例、已知内置代码和带生成标记的文件 | 730 | 179,863 | 12,870 | 5,410 | 198,143 |
| ECS 非测试源码 | 23 | 4,148 | 490 | 318 | 4,956 |
| ECS 排除生成文件 | 20 | 2,839 | 351 | 203 | 3,393 |

全部源码中 Go 占 **411,134** 有效行。`internal/brotli` 单独占 **252,414** 有效行，包含很大的静态字典表。因此不能把 46 万行直接理解成手写引擎逻辑的规模。第二种口径更适合观察日常维护规模，但不等同于严格的原创代码数量：内置代码依据显式清单排除，未标记的生成代码和其他衍生代码仍可能存在。

统计包括此次新增的 Python 脚本；新基准属于测试代码，被排除。完整语言和目录分布见 [统计原始结果](code-count-results.txt)。

### 下次运行

```sh
# 默认：全部非测试源码，输出语言及一级目录汇总
python3 scripts/count-code.py

# 单独统计 ECS，可逐文件查看
python3 scripts/count-code.py ecs --by-file

# 更接近日常维护规模的口径
python3 scripts/count-code.py --exclude-bundled --exclude-examples --exclude-generated
```

脚本路径：[scripts/count-code.py](../scripts/count-code.py)。依赖 Python 3.9+、Git、cloc。当前环境已将官方 cloc 1.98 单文件版本安装到 `~/.local/bin/cloc`；脚本先查 PATH，再查该路径。其他机器可安装发行版的 cloc，或用 `--cloc /path/to/cloc`。输出包含 cloc 版本，跨版本结果可能略有差异。

路径参数相对于仓库根目录，因此从其他工作目录启动也能使用。通过 `git ls-files --cached --others --exclude-standard` 收集当前文件，包含未提交且未忽略的新增源码；排除已删除文件和符号链接。相同内容的不同文件分别计数，不做内容去重。

默认排除文档目录、测试目录、`testdata`、常见测试/基准文件名、vendor、node_modules、构建输出以及非源码扩展名。JSON/XML 配置、图片、字体、二进制和 SPIR-V 不计入；HTML/CSS、文本着色器、Gradle 和脚本计入。扩展名及内置代码清单集中在脚本顶部，新增语言或引入代码时可更新。

`--exclude-bundled` 排除 Brotli、WebP、PNG 的 stdlib 文件、Vulkan 头文件、Wayland 生成协议、wasm_exec.js 和两份 Skia 衍生文件。`--exclude-generated` 检查文件开头 4 KiB 内初始注释头的生成标记，不扫描正文中的普通“generated by”描述。这些都是可检查的计数规则，不是许可证识别器。

GLSL/WGSL 和 `.inc` 借用 cloc 的 C 注释规则，着色器在汇总里单列。cloc 的 JSON 输出仅通过内存解析，不在仓库写入 JSON。若候选源码被 cloc 漏掉，脚本报错，避免静默输出不完整总数。

## ECS 优化建议

### 1. 优先处理空命令刷新和历史命令流扫描

位置：[FlushCommands/resetStorage](../ecs/commands.go)、[executeSystem](../ecs/schedule.go)。

每个成功执行的系统都会 `FlushCommands`。即使命令队列为空，也进入 defer 清理并遍历整个 `streamList`。流按世界生命周期缓存，当前系统可能只使用其中一个，甚至一个也没使用。令 S 为本帧执行系统数、H 为历史命令流数，清理开销可达到 O(S×H)。

| 历史流数 | 空 Flush 中位耗时 | 分配 |
| ---: | ---: | ---: |
| 0 | 13.02 ns | 0 |
| 64 | 176.1 ns | 0 |
| 1,024 | 2,525 ns | 0 |

建议分两步：先在世界与结构修改检查之后，对空队列直接返回；再为非空刷新记录本批活跃流，只清理这些流，复杂度由 O(H) 变成 O(H_active)。活跃列表和标志可复用容量，保持预热后零分配。需要覆盖失败、panic、回滚和下一批重新入队，保证引用清理与保留值索引正确。上表是合成历史流数量的微基准，不代表当前场景真的使用了 1,024 种命令。

### 2. 修正迁移计划首次绑定中的 O(C²) 查找

位置：[removalPlan.transition](../ecs/removal.go)、[patchPlan.transition](../ecs/patch.go)、[archetype.columnIndex](../ecs/archetype.go)。

虽然 ID 合并已经采用有序遍历，但遍历 `source.ids` 时又调用 `source.column(id)`；该函数从头线性扫描。目标列绑定也重复调用 `target.column(id)`。因此首次绑定仍是 O(C²)，Patch 还包含 O(K×C) 的写入列查找。历史报告里针对 ID 合并的 O(C+K) 结论不能覆盖整个 transition。

| 组件数 | Removal 首次绑定 | Patch 首次绑定 |
| ---: | ---: | ---: |
| 8 | 388 ns | 463.1 ns |
| 64 | 4,093 ns | 4,204 ns |
| 256 | 38,724 ns | 40,547 ns |

建议直接使用已对齐的 `source.columns[i]`，再用源/目标有序 ID 的双指针绑定目标列；Patch 的排序写入列表需保留调用者参数位置映射。可将绑定阶段降为 O(C+K)，无需引入每列 map。保留覆盖值的 Added tick、移除钩子及 swap-remove 行修正语义。

这些数字刻意重建 transition，但预热了目标 archetype，隔离的是绑定成本。Removal 每次 4 次分配、Patch 5 次分配；256 组件时分别为 12,016 和 12,208 B/op。正常缓存命中不重复承担这笔成本，优先级低于每帧发生的空 Flush；组件很少且原型稳定时收益有限。

### 3. 多空原型场景：查询成本依赖历史规模

位置：[queryPlan.update / nextArchetype](../ecs/query.go)、[createArchetype](../ecs/world.go)。

查询计划永久保留匹配的 archetype ID，每次查询仍遍历空表。世界中的 archetype 也不删除。只保留一个活实体，增加匹配但为空的原型，得到：

| 匹配原型数 | 单次查询中位耗时 | 分配 |
| ---: | ---: | ---: |
| 1 | 104.6 ns | 0 |
| 256 | 514.2 ns | 0 |
| 4,096 | 10,162 ns | 0 |

目前是 O(A_history + N_matches)。可考虑世界级非空原型 bitset 与查询匹配 bitset 求交，并按置位位枚举；扫描成本变为 O(A_history/word_bits + A_active + N_matches)。也可按非空状态版本缓存计划中的活跃表，但应实测维护成本。只在原型行数 0↔1 时更新占用信息，避免每次组件写入额外扫描所有查询计划。

该基准是极端碎片化场景，不能据此推断正常少量原型的场景也需要增加索引。`.In(...)`/QueryScope 会按借用实体列表逐项验证和绑定，是另一条路径。

### 4. 内存：区分零分配与峰值常驻

位置：[typedColumn.reserve/swapRemove](../ecs/component.go)、[World 的缓存](../ecs/world.go)、[messageBuffer.advance](../ecs/message.go)、[Commands](../ecs/commands.go)。

实体删除会清空引用、缩短切片，但列、实体元数据、free 列表、消息双缓冲和命令流保留容量。原型、查询计划和迁移边也会保留。这有利于复用，但场景大幅缩小后，内存不会跟随存活实体数下降；这属于高水位缓存，不能单凭这一点认定为对象泄漏。

建议先增加调试统计：存活行数与容量、空原型数、查询计划数、命令/消息容量及估算保留字节。若移动端场景切换确有问题，再提供显式闲置期 Trim/重建世界策略，保护活跃迭代器、缓存的 Spawner/Patch、预留容量和外部持有的组件引用。不要每帧 shrink，避免分配抖动。

每个实体的每个组件固定有 Added/Changed 两个 uint32 tick，即 **8 字节/组件行**，还没计入范围缓存、切片容量和组件值。100 万实体、每实体 6 组件，仅两组 tick 就约 **45.8 MiB**。若实测这部分占比过高，可研究注册时选择是否追踪变化；懒分配不能凭空恢复旧 Added/Changed 时间，不能直接在首次查询时补零。

### 5. 分散修改查询：有算法空间，但现有层级摘要已有效

位置：[nextBlock / rowMatches](../ecs/query.go)、[tickRange](../ecs/component.go)。

10 万行时，当前 Changed 查询的中位数：无变化 **345.8 ns**，一行变化 **842.7 ns**，每 64 行改一行 **309.3 μs**，全部变化 **553.2 μs**；均为 0 B/op、0 allocs/op。

每 64 行修改一行会命中几乎所有块，命中块内仍逐行检查 tick，实际只返回约 1/64 行，却检查近乎全部行。若真实工作负载长期如此，可研究候选行 bitset 或按 tick 分桶的修改索引，再用原有 tick 作精确验证。必须支持不同系统的读取窗口、多个读者、实体迁移及 tick 回绕；不能每帧统一清空脏位，否则慢读者漏变化。需要比较索引写入成本、保留历史成本及高修改密度回退路径。

现有无变化/单行变化非常快，因此此项属于按负载验证的中期方案，不能承诺总体更快。基准重复读取同一窗口，会受益于范围缓存，不等于包含所有写入成本的完整帧。

### 6. 冗余代码：先改手写重复，保留类型化热循环

- `query_iter.go`、`spawner_typed.go`、`patch_typed.go` 共 **1,309 有效行**，约占 ECS 的 **31.6%**，由 [internal/ecsgen](../internal/ecsgen/main.go) 统一生成。重复来自不同泛型参数个数，以及无过滤、变化过滤、受限实体遍历等路径。维护入口已经集中，不宜为了减少展开行数引入 `any`、反射或逐实体动态分派。
- `CommandSpawn` 与 `CommandSpawnPrepared` 的回滚和命令入队尾部可以提取小的共享函数；保留准备阶段 panic 后截断 `spawnEntries` 的处理。
- `Insert` 对新增列既调用 `componentColumn` 又调用 `columnIndex`；`Remove` 也查找移除列两次。保留列索引并直接复用可以减少重复扫描，不需要改变现有数据结构。
- `archetype` 结构注释仍写“mask test plus binary search”，实际 `columnIndex` 使用线性扫描；应同步注释。不要仅因理论复杂度将所有短列表改成二分，常见少组件路径需比较常数成本。
- cleanup 回调与实际移除分两遍具有语义意义：钩子需要看到完整源行。此处不能为“合并遍历”贸然边回调边删列。

建议实施顺序：**空 Flush → 冷绑定双指针及重复列查找 → 内存观测 → 按场景决定活跃原型索引、Trim 和修改行索引**。
